# Grok Bot 0.18 项目源码与架构解析

## 1. 结论先行

这是一个基于公开发行版二进制进行逆向重构的 Electron 桌面 Agent 应用。它不是原始产品 monorepo，也不是一个完全从零编写的普通 Electron 项目，而是由三类内容共同组成：

1. `source/` 下的可读 TypeScript 重构代码。
2. `frontend/` 下的部分 React/TypeScript Renderer 重构代码。
3. 通过 `npm run bootstrap` 获取的、经过 SHA-256 固定的官方 0.18.0 运行时输入。

因此，项目同时存在两种视角：

- **源码视角**：可以阅读和修改 Electron Main、Preload、Coordinator、Host、Agent、协议和部分 Renderer。
- **发行包视角**：最终 macOS 包是一个混合产物，使用官方 Electron shell/native ABI，编译部分重构运行时，并默认保留官方 Renderer 作为 UI 基线。

最重要的架构特征是：

> Electron Main 负责桌面生命周期和可信边界，Coordinator 负责跨进程编排，Host 负责 Agent 会话与工具执行，Remote Box 或 Local Docker 负责隔离运行环境，Renderer 通过 Preload 和 MessagePort 与后端通信。

整体运行结构如下：

```text
┌──────────────────────────────────────────────────────────────┐
│ Electron Main Process                                        │
│  窗口 / 账号 / 设置 / 密钥 / MCP / 更新 / Box / IPC / 遥测      │
└───────────────┬──────────────────────┬───────────────────────┘
                │                      │
       contextBridge / IPC      MessageChannelMain
                │                      │
┌───────────────▼──────────────┐ ┌─────▼────────────────────────┐
│ Renderer + Preload            │ │ Coordinator Utility Process   │
│ React UI                      │ │ Gateway / Provider / MCP      │
│ window.desktop                │ │ local-exec / WebAuthn / relay  │
│ window.coordinatorPort        │ └─────┬───────────────┬──────────┘
└──────────────────────────────┘       │               │
                                HTTP/SSE Gateway   外部 Provider
                                       │               │
                         ┌─────────────▼───────┐  ┌────▼──────────────┐
                         │ Host Process         │  │ Claude / Codex /  │
                         │ Extension Graph      │  │ OpenRouter        │
                         │ Session / Runner     │  └───────────────────┘
                         │ Transcript / Tools   │
                         └─────────────┬────────┘
                                       │ ConnectRPC / Protobuf
                         ┌─────────────▼──────────────┐
                         │ Box Exec Daemon             │
                         │ shell / read / write / GUI  │
                         └─────────────────────────────┘

      用户本机工具的另一条边界：
      Host local-exec extension → Gateway SSE → local-exec-daemon → 本机 shell/filesystem
```

## 2. 项目定位与源码边界

### 2.1 这不是原始源码仓库

官方应用只提供了编译后的 Electron 应用和优化后的 Renderer bundle，没有完整的原始前端源码、原始 source map、原始模块命名或原始注释。因此仓库中的名称和模块边界都是根据发行物、运行时观察、协议、字符串和可重复证据恢复出来的。

项目明确要求：

- 不把重构代码描述为官方原始源码。
- 不把重构包描述为官方发行版。
- UI 行为必须有 artifact anchor 或其他可检查证据。
- 构建成功和类型检查通过，不能单独证明行为来源正确。

这些边界记录在 `PROVENANCE.md` 和 `NOTICE.md`。

### 2.2 两个源码根

| 源码根 | 主要内容 | 是否等于原始源码 |
|---|---|---|
| `source/` | Electron、Host、Coordinator、Daemon、协议、Agent 库 | 否，属于可读重构 |
| `frontend/` | React Renderer、UI primitives、feature、状态控制器 | 否，属于部分证据驱动重构 |

`source/shared/` 也不是纯类型目录，其中 `source/shared/node/` 包含 Settings、Cursor Backend、实验和文件系统等 Node 运行时代码。

### 2.3 运行时输入与生成产物

| 路径 | 作用 |
|---|---|
| `research-archives/original/0.18.0/` | Git LFS 保存的官方 macOS arm64 和 Windows x64 安装包 |
| `src/app/dist/` | Bootstrap 后提取的官方应用运行时，默认被 Git 忽略 |
| `.cache/` | 下载包、挂载后的官方 App 等缓存 |
| `.build/` | esbuild/Vite、ASAR、完整性清单和中间 App 目录 |
| `dist/` | 最终 macOS `.app` 输出目录 |
| `recovered/` | 私有 forensic recovery 输出，默认不作为发布源码 |
| `manifests/` | 构建真正消费的 provenance、closure、binding 清单 |

## 4. 进程与运行时边界

### 4.1 Electron Main

入口：

- `source/electron-main/main.ts`
- `source/electron-main/main-production-services.ts`
- `source/electron-main/production-adapters.ts`

职责：

- 配置应用环境和单实例行为。
- 创建和管理 BrowserWindow。
- 初始化 Settings、safeStorage、账号、实验、MCP、更新和遥测。
- 创建 Remote Box 或 Local Docker connector。
- 启动、重启和销毁 Coordinator。
- 注册 Main RPC、Secrets IPC、MCP IPC 和 Coordinator Port IPC。
- 处理菜单、窗口快捷键、deep link、OAuth、WebAuthn、VNC 和退出流程。

启动入口 `startElectronMain()` 位于 `source/electron-main/main.ts:232-451`。

主窗口的关键配置是：

```text
contextIsolation: true
nodeIntegration: false
sandbox: false
webviewTag: true
```

这意味着 Renderer 不直接拥有 Node API，但当前设计仍关闭了 Renderer sandbox，并在 Main 中追加了 Electron `no-sandbox`。

### 4.2 Preload

入口：

- `source/electron-preload/runtime/primary.ts`
- `source/electron-preload/runtime/webview.ts`
- `source/electron-preload/runtime/vnc.ts`
- `source/electron-preload/preload.ts`

主 Preload 只向页面暴露受控对象：

```text
window.desktop
window.coordinatorPort
```

`window.desktop` 负责 Main 侧能力，例如账号、设置、密钥、MCP、附件、窗口、主题、权限、更新和遥测。

`window.coordinatorPort` 是一个 MessagePort Broker，用于取得 Coordinator 的 Renderer Data Port。

典型调用链：

```text
Renderer
  → window.desktop.someMethod()
  → Preload main edge
  → sand-rpc:main:m:<method>
  → Electron Main handler
```

VNC Preload 额外处理 clipboard、presence、liveness 和 Box desktop RPC；WebView Preload 处理 WebAuthn/passkey stall、popup 和受限导航。

### 4.3 Coordinator Utility Process

入口：`source/node-agent-coordinator/main.ts`。

Coordinator 由 Electron Main 使用 `utilityProcess.fork()` 启动，承担中间编排角色。它不是完整 Host，也不是 UI backend，而是把多个传输和执行域接在一起：

- 维护 Host Gateway HTTP/SSE 连接。
- 把 Renderer 请求路由到 Host 或外部 Provider。
- 管理外部 Provider 的直接推理。
- 启动和监督 `local-exec-daemon`。
- 转发 Host 的 transcript、agents、box、tool 和 settings 事件。
- 管理 MCP OAuth、WebAuthn signer 和 client-side-tool-v2 relay。
- 在 Coordinator 重启时处理端口替换、pending request 和 transport state。

Coordinator 通过三条逻辑通道与外部交互：

| 通道 | 对端 | 主要内容 |
|---|---|---|
| Control Port | Electron Main | 进程控制、账号、Box、MCP、遥测、WebAuthn、本机 Daemon |
| Renderer Data Port | Renderer | Agent、Transcript、发送消息、UI 事件 |
| Main Data Port | Electron Main | Host settings、附件、Box、Gateway 和部分 Main-side 操作 |

Coordinator 进程的组合入口为 `composeCoordinator()`，见 `source/node-agent-coordinator/main.ts:66-291`。

### 4.4 Host Process

入口：


- `source/host/main.ts`
- `source/host/sand-host.ts`

Host 是真正承载 Agent 后端的进程，负责：

- 启动 Host Extension Graph。
- 创建 Session、Agent DB、Transcript 和 Runner。
- 暴露 Host Gateway。
- 执行 Cursor inference、MCP、Auto Review、Memory、Automation 和 Sharing。
- 管理每个 Agent 的 Box 和工具资源。
- 管理 Host upgrade、恢复和优雅退出。

Host 可以运行在远程 Box，也可以运行在本机 Local Docker 容器中。Electron Main 不一定直接 spawn Host。

### 4.5 Box Exec Daemon

入口：

- `source/box-exec-daemon/main.ts`
- `source/box-exec-daemon/server.ts`

它运行在 Box 内，默认监听 loopback，并通过 ConnectRPC/Protobuf 提供：

- `ControlService.ping`
- `ControlService.updateEnvironmentVariables`
- `ControlService.loadMcpServers`
- `ExecService.exec`

其执行对象包括 shell、read、write、stream shell、background shell、stdin 和 terminal。

Host 默认可以自行启动它；当 `SAND_USE_EXISTING_BOX_EXEC_DAEMON=1` 时，则由容器或外部 supervisor 提供。

### 4.6 Local Exec Daemon

入口：`source/local-exec-daemon/main.ts`。

这是用户本机进程，不是 Box 内进程。它由 Coordinator/Main 监督，通过 Host Gateway 的专用 SSE/HTTP 通道接收请求，执行用户权限下的本机 shell 和文件操作，再把结果返回 Host。

它的身份校验依赖：

- generation token。
- PID 和进程存活状态。
- canonical entry path。
- discovery 文件。
- command line/entry identity。

## 5. Host Extension Graph

### 5.1 Graph 机制

Host 通过 `defineHostExtension()` 定义扩展：

```ts
{
  id,
  dependencies,
  start(context)
}
```

Graph 管理器位于：

- `source/internal/host-extensions.ts`
- `source/host/extensions/registry.ts`
- `source/host/host-production-extensions.ts`

启动前会校验：

- Extension ID 是否重复。
- 依赖是否存在。
- 是否自依赖。
- 是否存在循环依赖。

启动时按照拓扑顺序创建 API，并通过 `context.deps` 注入依赖。停止时则按照逆序执行 teardown。

当前注册表定义了 35 个 Extension slot。

## 6. Agent、Session、Transcript 和 Runner

### 6.1 内部 packages

`source/packages/` 不是独立 npm workspace，而是项目内的领域库集合。

| 包 | 职责 |
|---|---|
| `agent/` | Agent 主运行时、stream、checkpoint、summarization、redaction |
| `agent-core/` | interaction、conversation action、steering、MCP auth |
| `agent-exec/` | Resource Accessor、shell、MCP、subagent、background executor ABI |
| `agent-transcript/` | Transcript trace、summary、blob hydration 和 JSON/JSONL 输出 |
| `chat-inference/` | Provider-neutral prompt/session/executor 抽象 |
| `chat-inference-proto/` | Cursor inference Protobuf 和消息适配 |
| `context/` | Request context、取消、日志和 tracing |
| `local-exec/` | shell、read、ls、background shell 等具体执行器 |
| `proto/` | Agent、Box、Exec、Control、Inference、MCP 生成代码 |
| `shell-exec/` | 基础 Shell executor |
| `mcp-agent-exec/` | Agent 侧 MCP 执行支持 |

Agent 不直接绑定某个具体 Box。它通过 `agent-exec` 的资源抽象取得执行器，Host 在 Runner Composition 阶段把本地资源和远程 Box 资源注入进去。

### 6.2 一次 Cursor turn

Cursor 是默认 Provider，典型链路如下：

```text
Renderer
  → Coordinator Renderer Data Port
  → POST /api/sendPrompt
  → Host Gateway API
  → Transcript send pipeline
  → Turn Runner
  → Host inference extension
  → Cursor Backend / Protobuf
```

Host turn 的主要阶段是：

1. 读取和准备 Transcript。
2. 写入 user echo、acceptance ledger 和 ack obligation。
3. 组装 system prompt、Agent profile、memory 和 MCP 上下文。
4. 确保当前 Agent 的 Box ready。
5. 创建 local/remote Resource Accessor。
6. 创建 Agent Runner。
7. 执行推理、工具、subagent、Auto Review 和 computer use。
8. 将流式 update 写入 Transcript/Event Bus。
9. checkpoint、settle，并恢复 background work。

主要实现：

- `source/host/host-runner-composition.ts`
- `source/host/runner-production-bridge.ts`
- `source/host/runner/turn-run-shell.ts`
- `source/host/extensions/transcript/`

## 7. Host Gateway 与通信协议

### 7.1 Gateway API

Host Gateway 由以下文件组成：

- `source/host/gateway-server.ts`
- `source/host/gateway-protocol.ts`
- `source/host/host-gateway-api.ts`

主要端点：

```text
POST /api/<method>          Gateway command
GET  /events                Host SSE event stream
GET  /health                Host health
GET  /avatars/<agent>      Agent avatar
POST /prepare-upgrade       Upgrade quiesce
GET  /local-exec/requests   本机执行请求流
POST /local-exec/responses  本机执行结果
GET  /webauthn/requests     WebAuthn 请求流
POST /webauthn/responses    WebAuthn 结果
```

Gateway command 覆盖：

- Agent 创建、删除、更新、搜索和 roster。
- Transcript 加载、分页、Thread、Prompt acceptance。
- Prompt 发送、Reaction、Widget、Secret 和 Auto Review。
- Automations、Workflows 和 Scheduled wake。
- Shared Room、Cloud Agent 和 Channels。
- MCP、Plugin、Skill 和 Routed MCP。
- Box 状态、Box recreate、Host upgrade 和磁盘压力。
- Attachment、Teach Recording、WebAuthn 和 local-exec。

### 7.2 Gateway 安全策略

`gateway-server.ts` 的安全策略包括：

- 有 `authToken` 时要求 Bearer token。
- 无 token 时仅接受 loopback host。
- 带浏览器 `Origin` 的请求直接拒绝。
- token 比较使用 `timingSafeEqual`。
- Request body 有大小上限。
- SSE 带 heartbeat，可按 channel 过滤，并支持 gzip。
- Avatar 响应使用禁止执行内容的响应头。

### 7.3 Coordinator MessagePort 协议

共享协议定义在 `source/shared/rpc/coordinator-port.ts`，协议版本为 `1`。

Frame 类型：

```text
lifecycle: hello / ready / shutdown
request
cancel
reply
event
```

请求和回复通过 `requestId` 关联，回复 envelope 为：

```ts
{ status: "ok", value }
{ status: "failed", failure: { code, message, transportKind? } }
```

Renderer 当前使用的 client 是：

- `frontend/src/production/coordinator-client.ts`

该 client 负责：

- claim 和替换 transferred port。
- 等待 Coordinator `ready`。
- 发送 request 并匹配 reply。
- 转发 event family。
- 在断线时 reject pending calls，并重新请求端口。

注意：`frontend/src/recovered/runtime/coordinator-source.ts` 还保留着另一套更完整的恢复版 Coordinator source/claimant。它不是当前 ProductionRenderer 直接使用的 client，属于潜在实现漂移点。

## 8. 推理 Provider 架构

Provider 定义在 `source/shared/inference-router.ts`：

```text
cursor
claude-code
codex
opencode
openrouter
```

### 8.1 Cursor Provider

Cursor 路径经过完整 Host turn runner：

```text
Renderer
  → Coordinator
  → Host Gateway
  → Host Transcript / Runner
  → Cursor inference
  → Cursor Backend
```

它会参与：

- Host Transcript 持久化。
- Privacy mode。
- Box ready 检查。
- 工具和 Auto Review。
- checkpoint 和 settle。
- Host event stream。

### 8.2 外部 Provider

Cursor Agent、Claude Code、Codex、OpenCode、OpenRouter 由 Coordinator 直接路由：

```text
Renderer
  → Coordinator inference-router
  → Host transcript tail
  → coordinator 本地 transcript
  → 外部 Provider
  → Routed MCP tool
  → 流式 transcript/event
  → inference-router-transcript.json
```

实现位置：

- `source/node-agent-coordinator/inference-router.ts`
- `source/host/extensions/inference/provider-session.ts`
- `source/host/extensions/inference/codex-direct-responses.ts`

Provider 方式：

| Provider | 调用方式 | 认证来源 |
|---|---|---|
| Claude Code | Claude Agent SDK / 本机 Claude CLI | `~/.claude/.credentials.json` 或环境变量 |
| Codex | 直接调用 Codex Responses SSE API | `~/.codex/auth.json`，支持 refresh |
| OpenCode | 本机 OpenCode CLI `opencode run --format json` | `~/.local/share/opencode/auth.json` 等 OpenCode auth 文件 |
| OpenRouter | `ai` SDK + OpenAI-compatible API | `OPENROUTER_API_KEY` 或 Desktop secrets |
| Cursor Agent | 本机 `cursor-agent --print --output-format stream-json` | Cursor Agent CLI 登录态 |

Codex 直接传输层明确支持：

- SSE text delta。
- usage 统计。
- function call。
- 使用原始 call id 的 tool continuation。
- `store: false`。
- 截断或不完整 SSE 的 fail-closed。

外部 Provider 与 Cursor 不共享完全相同的 Host turn 生命周期，这是 Provider 架构中最重要的分叉。

## 9. MCP、工具与执行边界

MCP 横跨多个层次：

```text
Electron Main MCP
  ├── Plugin 安装/卸载
  ├── OAuth 和账户
  ├── Desktop MCP 管理
  └── MCP IPC

Host MCP Extension
  ├── MCP server/tool 状态
  ├── Box MCP
  └── Host-side execution

Coordinator Routed MCP
  ├── listRoutedMcpTools
  ├── executeRoutedMcpTool
  └── 临时 localhost HTTP MCP bridge
```

外部 Provider 的 tool loop：

```text
Provider
  → tool definitions
  → executeRoutedMcpTool
  → Main-side MCP service / Host routed handler
  → MCP server
  → tool result
  → Provider continuation
```

Claude Code 使用临时本地 HTTP MCP bridge；bridge 绑定 `127.0.0.1`，并使用随机 secret 限制访问。

### 9.1 Box 工具

```text
Agent Tool
  → remote Resource Accessor
  → HostBox / LoopbackSandBox
  → ConnectRPC ControlService / ExecService
  → box-exec-daemon
  → Box shell/filesystem/desktop
```

### 9.2 本机工具

```text
Agent Tool
  → local-exec extension
  → Host Gateway /local-exec/requests
  → local-exec-daemon
  → 本机 shell/filesystem
  → /local-exec/responses
  → Host
```

本机工具的权限不是只在 UI 层判断，而是由 Host permission gate、approval/retirement 文件和 local-exec-daemon 二次校验共同控制。

## 10. Remote Box 与 Local Docker

### 10.1 Remote Box

Remote Box 由 Backend Broker 创建和管理：

```text
Electron Main
  → GrokBotService.ensureSandBox()
  → gatewayUrl / gatewayToken / networkToken / VNC URL
  → Coordinator Gateway Client
  → Host Gateway
```

主要实现：

- `source/electron-main/box/box-host-connector.ts`
- `source/electron-main/box/gateway-descriptor-cache.ts`

支持：

- Box 创建、重建和强制重建。
- Gateway descriptor 缓存和快速连接。
- Network token 和 VNC proxy。
- Local-exec credential。
- External Provider inference credential。
- Backend update-required 和 Box blocked 状态。

### 10.2 Local Docker

实现：`source/electron-main/box/local-docker-host-connector.ts`。

默认值：

```text
image:     public.ecr.aws/k0i0n2g5/cursorenvironments/universal:sand-box-latest
container: grok-bot-local-vm
```

启动流程：

1. 检查 Docker daemon。
2. 读取当前 Provider 和 Settings。
3. 对 Host bundle 和 `box-exec-daemon` 计算 SHA-256。
4. 将运行时写入 content-addressed 目录。
5. 检查现有容器的 owner label、image、schema、port 和 runtime hash。
6. 容器不匹配时删除并重建。
7. 只向 loopback 发布 Gateway、Exec、VNC 等端口。
8. 只读挂载 Host、Box Daemon 和可选 Provider credential。
9. 等待 `/health` 成功后交给 Coordinator 连接。

Local Docker 会设置：

```text
SAND_USE_EXISTING_BOX_EXEC_DAEMON=1
SAND_INFERENCE_PROVIDER=<selected-provider>
SAND_GATEWAY_TOKEN=<local-token>
```

它也可能只读挂载：

```text
~/.codex  → /root/.codex
~/.claude → /root/.claude
```

这使 Local Docker 方便复用本机登录态，但同时扩大了容器运行时的信任边界。

### 11.5 发送消息与 Transcript reconcile

前端发送消息不是简单的一次 RPC，而是一个带乐观状态和服务端 echo 合并的流程：

- Agent、账号或 Coordinator generation 变化时阻止旧请求回写。

| `src/app/dist/renderer` | 官方 0.18 Renderer artifact，默认 macOS fidelity package 的 UI 基线 |

直接执行 `npm run frontend:build` 可以构建可读 Renderer，但不等于默认 macOS 包就会使用它。

- Settings 采用 read-modify-write，并通过临时文件加 rename 完成原子替换。

- Agent DB 使用 Node SQLite/WAL。
- Blob、Transcript mirror、搜索索引和 Box store vacuum 使用 Worker Thread 或后台 Worker。

**Clean-source Renderer**

## 16. 关键风险与维护重点

### 高风险

1. **源码与最终运行时存在双重事实来源**

   `source/`、`frontend/`、`src/app/dist/`、artifact fallback、production activation 和最终 `.app` 同时存在。修复源码后，必须检查对应 runtime 是否真的被 overlay 到最终包。

2. **本机执行和 Electron 安全边界较宽**

   Main 窗口设置 `sandbox: false`，local-exec 最终执行用户权限下的 shell。Renderer XSS、恶意本机进程、approval 文件滥用或 connection descriptor 篡改，理论上都可能扩大为本机命令执行或凭据外发。

3. **外部 Provider 绕过完整 Host Turn Runner**

   Claude Code、Codex、OpenRouter 在 Coordinator 内直接执行。它们和 Cursor 在 privacy、审计、checkpoint、Transcript 一致性、重试和工具审批方面不一定完全等价。

4. **Local Docker 复用本机 Provider credentials**

   Local Docker 可能只读挂载 `~/.codex` 和 `~/.claude`。容器 image、挂载 runtime 和 Host bundle 必须被视为高信任组件。

### 中高风险

5. **Coordinator 协议复杂且存在并行实现**

   当前 Production Renderer 使用 `production/coordinator-client.ts`，恢复目录还存在 `coordinator-source.ts` 和 `coordinator-source-claimant.ts`。三条 MessagePort、SSE、重启、replay 和 generation fencing 叠加后，容易出现 cancel、旧事件、pending request 或 reconnect 语义漂移。

6. **多进程持久化没有统一事务边界**

   Settings 是进程内 read-modify-write。Main、Coordinator、Host 可能同时写相关状态；Agent DB busy 时还存在“请求已接受但消息未持久化”的窗口。

7. **ProductionRenderer 组合根过大**

   账户、Roster、Transcript、Composer、Computer、Settings、Plugins、Onboarding 和大量 Overlay 都集中在一个根组件中，长期维护时容易出现 effect、scope、dispose 和浮层优先级问题。

8. **部分恢复功能只有契约，未形成完整产品路径**

   已知例子包括 tool-result card 的 action seam、computer overlay 空实现、terminal output 未进入生产图，以及 PDF worker/部分动态 view 的证据缺口。

9. **CI 没有验证真实发行包**

   当前 CI 不验证 macOS `.app` 启动、native ABI、Docker、Host/Coordinator 完整启动、VNC、真实 Provider 或 local-exec 全链路。

10. **Docker image 使用 mutable tag**

    Local Docker 默认使用 `sand-box-latest`，相同源码在不同时间重建时，容器基础环境可能发生变化。

## 18. 最终架构总结

这是一套：

```text
Electron 桌面壳
  + Preload/contextBridge 安全桥
  + Coordinator 多端口编排进程
  + Host Agent 后端和 35-slot Extension Graph
  + Remote Box / Local Docker 隔离执行环境
  + Box/local-exec 双执行边界
  + Cursor / Claude Code / Codex / OpenRouter 多 Provider
  + HTTP/SSE、MessagePort、ConnectRPC/Protobuf 多协议
  + SQLite、文件、safeStorage 和 content-addressed runtime
  + provenance/closure 驱动的混合构建系统
```

它的优势是运行时边界和故障隔离设计比较清晰，能够同时支持官方 Cursor 流程和外部 Provider；它的根本复杂性则来自“逆向恢复 + 多进程 Agent + 保真发行包”三者叠加。维护时最需要优先确认的不是某个单独函数，而是：

1. 当前修改最终进入了哪个 runtime composition。
2. 当前请求走的是 Cursor Host 路径还是 Coordinator external Provider 路径。
3. 当前工具执行发生在 Box 还是用户本机。
4. 当前状态属于 Main、Coordinator、Host 还是 Renderer 的哪个持久化/快照 owner。
5. 当前 Renderer 结论是 clean-source evidence，还是官方 fidelity artifact 的行为。
